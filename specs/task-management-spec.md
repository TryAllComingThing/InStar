# Task Management SPEC V1.0

## 1. 目标

在现有测试工程中开发任务管理功能，验证 InStar 基于 SPEC 的真实代码开发能力。

## 2. 数据模型

- id：任务唯一标识。
- title：任务标题，必填，去除首尾空格后不能为空。
- priority：low、medium、high。
- status：todo、doing、done。
- createdAt：创建时间。

## 3. 功能需求

**FR-01 创建任务**

输入 title 和 priority，创建任务，默认状态为 todo。

**FR-02 查询任务**

支持查询任务列表及根据 ID 查询单个任务。

**FR-03 更新任务状态**

根据任务 ID 将状态更新为 todo、doing 或 done。

**FR-04 输入校验**

标题为空、优先级非法、状态非法时必须拒绝请求或提交。

**FR-05 错误处理**

不存在的任务返回明确的错误，不允许静默成功。

## 4. 后端 API 契约

- POST /tasks：创建任务，成功返回 201。
- GET /tasks：查询任务列表，成功返回 200。
- GET /tasks/{id}：查询单个任务，不存在返回 404。
- PATCH /tasks/{id}/status：更新状态，不存在返回 404。
- 非法输入返回 422。

## 5. 前端验收

- 显示任务列表。
- 提供新增任务表单。
- 支持修改任务状态。
- 对非法输入展示明确错误。
- 提供加载、空数据和失败状态。
- 使用 Mock API 完成独立测试，不依赖真实后端启动。

## 6. 工程约束

- 保留原有工程结构与技术栈。
- 不引入与任务无关的功能。
- 必须新增自动化测试。
- 不允许删除或绕过原有测试。
- 不允许通过修改测试期望掩盖产品缺陷。
- 必须执行项目适用的质量检查。
- 必须生成可追溯的质量报告。

## 7. 验收标准

- 所有功能需求均有对应测试。
- 所有适用的质量检查通过。
- 故意注入的失败必须被质量门禁识别。
- 修复后重新执行全部检查。
- 质量报告与原始执行证据一致。
