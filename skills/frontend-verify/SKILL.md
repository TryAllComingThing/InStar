Read the current change artifacts and [testing guidance](../../templates/engineering/testing.md). Identify the implementation under review and the real available commands before testing. Plugin tooling tests do not validate the target product.

Map applicable requirements and scenarios to implementation evidence and tests. For removed behavior, check that it is gone; for renamed requirements, do not demand renaming code symbols. Check task acceptance criteria against actual evidence rather than trusting checkboxes.

Run the checks required by the selected profile and proportionate to the change: configured lint and format checks, type/static checks, relevant unit/component tests, production build, and critical browser journeys. UI changes also require an automated accessibility check (for example Playwright + axe-core) and a keyboard/focus journey; a manual source inspection is not an accessibility pass. Inspect applicable loading, empty, error, responsive, keyboard and focus behavior. Record commands, observed results, artifact paths and screenshots. Do not claim a browser check when only source inspection was possible.

Do not run three equivalent browser gates. Use headless Playwright as the mandatory functional regression check, a separate axe run as the mandatory accessibility check, and headed Chrome only for optional human visual/interaction evidence. A page-load smoke script is fast feedback and may support the browser check, but it does not replace functional journeys, axe, or keyboard/focus evidence. Keep the `browser`, `accessibility` and `keyboard` artifacts distinct.

Report blocking defects with reproduction steps and concrete source references. Distinguish warnings from confirmed failures. Mark unavailable checks Not verified with a reason, not passing. Product corrections can continue within the user's authorized scope; requirement/design changes return to the planning workflow.

Summarize verified behavior and remaining limits for human acceptance. Never set `accepted: true` from your own assessment. After real acceptance the caller can use the promotion adapter described in the [workflow guide](../requirements-workflow/references/controller.md).

Use submit-implementation for pre-approval readiness: code/architecture review, `quality-gate`, and the `implementation` profile require `lint`, `format`, `test` (UI also `browser`). Implementation approval always requires `.instar-quality.json` and current quality-gate evidence. After the separate implementation approval, use submit-verification with the `full` profile: `security` (UI also `accessibility` and `keyboard`) and the stack verify Skill. Frontend/fullstack UI verification also requires a completed `frontend-reviewer`; UI requires `ui-reviewer`. `full` is an extension gate; do not repeat an identical browser command when the same source, configuration and check definition are already approved. When schema 3 defines the matching profile, include the configured `checkId`, generated report `reportId`, and real `artifact`; schema 1/2 uses labelled `source: "manual"` evidence. The controller verifies report, definition and artifact hashes, rejects stale evidence, and requires valid JSON semantics for browser/accessibility/keyboard artifacts. Failed, unverified or unresolved critical/warning findings block progression. If code changes after implementation approval or verification, invalidate the previous approval and evidence before rechecking.

Record measured Token/API usage with `record-usage` after material verification or reviewer calls when available. The SessionEnd Hook also imports Codex session usage; never estimate or invent missing historical values.

## Profiles and legacy compatibility

Read the [quality protocol](../../docs/QUALITY.md). The `implementation` profile requires at least `lint`, `format` and `test`, plus `browser` for UI changes; projects may add typecheck or build checks. The post-approval `full` profile adds `security`, plus `accessibility` and `keyboard` for UI. `commit` remains for pre-commit compatibility. The CLI action is `frontend-verify`; `local-verify` is a legacy alias. Do not repeat an identical browser command in `full` when it is already bound to the same source snapshot and check definition.

Use local file/Git reads and project npm scripts inside the host sandbox. Use the quality CLI, not `npx`, to download tools. Vite verification reuses the completed build manifest; dependency checks use lockfiles and installed dependencies. In schema 1/2, `tools.security` must map to a project script and runs only in `full`; schema 3 uses an explicit `security` check. A configured visual-regression script runs only in `full`, and the project owns its baseline snapshots. Accessibility must map to a real script that produces reviewable JSON or screenshots; otherwise record `not-verified`, never a browser smoke test as an axe pass.

Schema 3 reports are written to `reports/engineering-verify-<profile>.json`; schema 1/2 reports remain `reports/frontend-verify-<profile>.json`. A missing, failed, timed-out or source-changed check blocks and stops later execution. `logs/` records execution summaries without raw output. Plugin tests never replace target-project tests; after code or commit changes, verify again. Continue with [quality-gate](../quality-gate/SKILL.md) and [ci](../ci/SKILL.md) when applicable.
