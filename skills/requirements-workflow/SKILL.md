Use this Skill to keep a change inside the controlled lifecycle. It selects specialist Skills, preserves human approval boundaries, and records Skill/reviewer/usage evidence.

Do not use it for a source-only baseline, a single PRD revision, or a small existing-code change that does not need PRD/Spec/Design/Tasks. Use [spec-discover](../spec-discover/SKILL.md) for current-state discovery, [write-a-prd](../write-a-prd/SKILL.md) for PRD authoring or revision, and the lightweight path for small authorized changes.

## Workflow entry

Read the [controller protocol](references/controller.md). Resolve the explicit project path and change ID. If the project is not initialized, use initialize-project. Before resuming, read state; never infer the stage from conversation memory or file names.

Requests to reverse-document existing behavior from source use [spec-discover](../spec-discover/SKILL.md) instead. They need no synthetic PRD or implementation lifecycle; do not route them into start/approve/archive. New behavior changes still use this workflow.

For each specialist Skill invocation in a tracked change, record `trace-skill` events with one stable `invocationId`: `started` before applying it, followed by exactly one `completed` or `failed`. The controller rejects terminal events without a matching start and rejects reuse of a terminal invocation. Include the current stage and a brief non-sensitive summary. This is an agent-reported audit trail, not proof of execution.

Start every tracked change with an explicit `ui` boolean and `stack` (`frontend`, `backend`, or `fullstack`). If `context.emptyProject` is true, skip architecture/reference exploration and record that fact; still keep the classification, PRD/Spec gates and human approvals. UI designs must complete `design-check` and pass its `constraints`/`coverage`/`sources` to `write-design`; coverage must include hierarchy, layout, states, tokens, responsive and accessibility, with non-applicable categories stated explicitly. UI implementation readiness must include browser evidence; post-approval verification must include accessibility and keyboard evidence without rerunning the same browser check for the same source snapshot. Before `submit-implementation`, complete the stack implementation Skill, `quality-gate`, `architect`/`code-reviewer` reviews, and the `implementation` checks; implementation approval always requires `.instar-quality.json` and current quality-gate evidence. After that approval, complete the stack verify Skill, `security-reviewer`, and for frontend/fullstack UI `frontend-reviewer`, plus `ui-reviewer` for UI, and the `full` checks before `submit-verification`. Record each reviewer with `trace-agent`, including real `reviewedFiles`, findings, and `executionMode`; critical/warning findings or unverified checks block, and never label a main-agent fallback as a subagent. Small existing-code changes may use the documented lightweight path instead of synthetic PRD/Spec documents.

Before `submit-spec` can open human Spec review, complete `spec-reviewer` with `trace-agent` at the Spec stage. Its report must cover the proposal and delta specs and is bound to their current content hash. Critical or warning findings and unverified items block submission; after any Spec edit, rerun `spec-reviewer`.

Record Token/API consumption with `record-usage` when a Skill or reviewer call has measured usage. The SessionEnd Hook also imports Codex session usage into `reports/usage/` when available. Never estimate missing historical tokens; report them as unavailable. If `usageBudget.enforce` is enabled and the budget is exceeded, use `set-usage-budget` to raise, disable, or clear it before the next controlled transition.

## PRD review loop

Use [write-a-prd](../write-a-prd/SKILL.md) for initial authoring and **every round of PRD revision**, including follow-up messages such as “补充需求”, “修改 PRD”, “还需要调整” and “按审核意见修改”. Announce its use for each authoring/revision round. Load its instructions if not already available; reusing loaded instructions is valid, but merely calling save-prd is not evidence that the writing skill was used.

1. For a new change, use write-a-prd to author and persist the PRD with start, run quality-evaluation at stage `prd`, then submit-prd. Show the document, evaluation status/report, assumptions, unresolved decisions and current review hash. Stop at this boundary.
2. For revision feedback while pendingApproval=prd, record request-changes with the actual feedback. Read the current PRD and feedback, use write-a-prd to revise it, save-prd with the latest version, rerun quality-evaluation at stage `prd`, then submit-prd again. Show the revised document, evaluation, changes made, remaining questions and new review hash. Wait for a fresh approval of that version. Repeat this loop as often as requested; do not create a new change for each round.
3. If already editing PRD, continue with write-a-prd and save-prd without request-changes. If the PRD was approved and later business feedback changes it, reopen prd with the actual reason, use write-a-prd, and repeat its review. This invalidates downstream approvals and generated plans.
4. Only explicit approval of the shown, unchanged PRD permits approve with its current hash and the actual reply/source. Then use spec-explore, spec-propose and spec-verify. If exploration changes business requirements, return to the PRD loop.

## Spec review loop

1. From the approved PRD, use spec-propose for proposal and complete delta specs, then spec-verify and quality-evaluation at stage `spec`. Correct blocked findings through spec-propose and rerun both evaluations. Complete `spec-reviewer` against the final proposal/deltas; the controller rejects submission without a current completed review. A passing gate plus clean reviewer evidence permits human review, not design generation.
2. Show proposal, delta specs, deterministic gate, spec-reviewer findings and current review hash. Stop at the human Spec boundary.
3. For Spec revision feedback within the approved PRD scope, use request-changes when pendingApproval=spec, then spec-propose with fresh context and save-spec, followed by spec-verify, quality-evaluation at stage `spec`, and submit-spec. Show the revised package, evaluation, changes and new hash; repeat human review until explicitly approved. If already blocked/editing, revise without request-changes. Feedback that changes PRD business scope returns to write-a-prd through reopen prd and requires renewed PRD approval before regenerating Spec.
4. Only explicit approval of the shown, unchanged Spec permits approve and handoff to spec-design. For UI work, invoke design-check before write-design and pass its Style Constraints and sources. Run quality-evaluation at stage `design` after `technical-design.md`. Show the technical design and wait for its separate `design` approval. Then use spec-tasks and run quality-evaluation at stage `tasks`; show the numbered task list and wait for its separate `tasks` approval. Only that task approval authorizes implementation. If a previously approved Spec needs revision, reopen spec and repeat its loop.

## Interpreting review replies

Questions or requests to explain a document do not approve or reject it; answer while preserving pending review. A reply such as “可以，但补充……” that requests document changes is revision feedback, not approval of the resulting unseen version. Never use approval of an earlier version, silence, a passing report, or “继续修改” to cross a review boundary. If the intended decision is genuinely unclear, clarify while retaining the current pending review.

When approval is explicit, call `approve` with one of three decisions: `accept-record` (default; store the human reply and source), `accept-no-record` (advance without persisting the reply text), or `reject` (requires feedback and returns to the editable stage). `request-changes` remains the shorthand for rejection. Audit records such as `trace-skill`, `trace-agent`, `record-usage`, and controller writes under `planning/`, `reports/`, `logs/` and `.workflow/` are automatic and must not trigger a separate confirmation prompt. Source/config edits, deletion, commit, push, PR creation and deployment still require authorization.

## Implementation and acceptance

After explicit task-list approval, select `engineering-implement` for backend/cross-stack work or `frontend-implement` when UI/Vue conventions are central. When coding is complete, run code and architecture conformance review, the project `implementation` checks, and `quality-gate`, then submit-implementation for a separate human implementation-readiness approval. Only after that approval run `engineering-verify`/`frontend-verify` with the `full` profile and the post-approval security/UI gates. Block on failed/unverified applicable checks; correct and recheck. The controller binds implementation approval and verification to source snapshots and blocks archive if source/config changed afterward. Show verified behavior and evidence for human acceptance. Record actual acceptance, then archive and verify the four archived artifact groups: proposal, all delta specs, technical design, and task list. The PRD stays at `docs/prd/<changeId>.md`; `workflow.json` is archived alongside those groups.

For a small existing-code change that does not require synthetic PRD/Spec/Design/Tasks, follow the [lightweight path](../../docs/WORKFLOW.md#轻量路径) only within the user's explicit authorization; it remains subject to the project implementation checks, `quality-gate`, reviewer evidence, and commit/full profiles.

Keep workflow and specialist skills as separate entrypoints. Use engineering-research before unfamiliar integrations, systematic-debugging for unexplained failures, and context-optimizer only when context quality is a demonstrated blocker. The main agent orchestrates; reviewers are read-only and do not approve. Run spec-reviewer before Spec review, and run the relevant architect/code/security/UI reviewers before verification. If an independent Subagent cannot run, perform the review in the main agent and record `executionMode: "main-agent-fallback"`; never claim a missing reviewer ran. No automatic approval, approval from silence, or bypass of a blocked gate.

A user’s confirmation applies only to the artifact version shown. Record their actual response and conversation source; never fabricate either. Controller hashes detect reviewed document changes and the source fingerprint detects source changes after verification, but neither authenticates human identity or proves checks ran. For changes to reviewed inputs use reopen at the earliest affected stage. For implementation edits after verification, reopen implementation and verify again. Preserve failures and report concrete deviations before continuing dependent work.

## Success criteria

The workflow is complete only when the current state matches the reported stage, every required human approval is bound to the shown artifact version, all specialist and reviewer evidence is current, applicable checks are not failed or unverified, and no gate was bypassed. Archive only the reviewed artifact set, then report the archived paths, final evidence and any remaining limitations.
