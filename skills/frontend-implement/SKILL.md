---
name: frontend-implement
description: Implement authorized frontend tasks from reviewed specifications and design, with task-level verification. Use after planning, not for PRD or Spec authoring.
compatibility: Requires the full InStar plugin package; plugin-root templates and design guidance resolve from the installed plugin root.
---

Read applicable `AGENTS.md` instructions from the project root through the target file's directory, plus any configured or discovered project architecture and design documents, relevant project `standards/` documents, [frontend conventions](../../templates/engineering/frontend-conventions.md), [testing guidance](../../templates/engineering/testing.md), and the selected change's current proposal, delta specs, `technical-design.md` and tasks. Context documents are optional: use the project's existing canonical locations or `.instar-quality.json` `context` paths; do not create duplicate copies just to satisfy InStar. Confirm the user authorized implementation and that the planning artifacts are present. Do not infer permission from a task file alone. Project rules govern; plugin conventions fill gaps and never override them.

Use [InStar engineering references](../../standards/README.md) selectively. Identify the changed files' language and load only its guide from [language packs](../../standards/languages/README.md). For API work, consult the [API design specification](../../standards/api/api.md); for persistence work, consult the [database schema specification](../../standards/database/schema.md), [query specification](../../standards/database/query.md), [migrations](../../standards/database/MIGRATIONS.md), and the matching engine guide. For tracked UI work, invoke [design-check](../design-check/SKILL.md) before implementation and consume its recorded constraints; do not skip it merely because the visual change looks small. Read the project's canonical design document, design-system manifest, and token sources first. Only when the project has no design source may you consult [design guidance](../../design-guidance/DESIGN.md) and applicable rules for [visual language](../../design-guidance/rules/visual-language.md), [tokens](../../design-guidance/rules/tokens.md), [components and interaction](../../design-guidance/rules/components-and-interaction.md), [layout](../../design-guidance/rules/layout-and-responsive.md), and [accessibility](../../design-guidance/rules/accessibility.md); read [theming](../../design-guidance/rules/theming.md) only when the project explicitly supports multiple themes, tenant branding, or user-selectable appearance. Never use plugin visual examples or concrete visual values as project facts. Do not introduce frameworks, database abstractions, theme engines, token systems, or styling architectures unless the user or project requires them.

Work in dependency order. Before each task, inspect relevant existing components, tests, styles, and request/state boundaries. Follow the technical design's Architecture and File Change Plan against the current source tree. Prefer existing project patterns. The approved `designReuse` items are binding evidence: reuse the named components/patterns or follow the approved `designReuseReason`; do not introduce a parallel component, pattern, or token system without returning to design approval. For a new application, resolve its framework and setup in the first relevant task; this workspace does not choose one for you.

For observable behavior changes, add a focused failing test where the project supports a suitable test; then implement the behavior and run the test. Use browser/visual checks for UI outcomes that unit tests do not establish. Avoid tests that merely mirror implementation. If no suitable test framework or meaningful automated test exists (for example, a documentation-only or purely presentational change), state why and use proportionate alternative verification; do not add a test framework solely to satisfy TDD. Deliver each task's relevant tests and documentation with that task.

Route specialized work on demand: use [engineering-research](../engineering-research/SKILL.md) before adding a dependency, integrating an unfamiliar API, or writing a helper that may already exist; use [systematic-debugging](../systematic-debugging/SKILL.md) for unexplained failures or bugs. Use [context-optimizer](../context-optimizer/SKILL.md) only when project instructions are bloated, conflicting, stale, or causing repeated rediscovery. These skills supplement this implementation workflow; they do not replace its authorization, task evidence, TDD, or verification requirements.

Keep loading/error/empty states, accessible controls, keyboard behavior, and responsive layout aligned with the requirements. If implementation uncovers a requirement or design contradiction, report it and return to the affected planning stage; do not silently modify reviewed artifacts or fingerprint records.

Mark only completed canonical task checkboxes `[x]` after their acceptance evidence exists. Preserve task text and numbering; changing them invalidates the engine's fingerprint. Use one `complete-tasks` batch with `{taskId,evidence:{summary,files:[{path,line,note}],verification}}` entries so the controller can validate every task and commit the checkboxes in one transaction; `complete-task` only remains as the final-task or legacy compatibility path. A free-text claim is not sufficient for a schema-version-2+ workflow. Report completed work, actual verification and blockers. Use frontend-verify for final implementation checks. Do not promote or claim human acceptance on the user's behalf.

When `.instar-quality.json` defines `verification.layers`, iterate with L1 changed-unit checks and run L2 once against the stable implementation snapshot before submit-implementation. Reuse L1/L2 evidence only through the controller's exact cache key; do not repeatedly run the post-approval full profile during task iteration. L3 frozen-full runs once after implementation approval.

Read the [controller protocol](../requirements-workflow/references/controller.md). Require current implementation authorization before coding. Trace this Skill with `started`/`completed` and record tasks through `complete-tasks` with structured evidence; do not check boxes directly. Use frontend-reviewer for read-only review during implementation when available; it is mandatory at verification for frontend/fullstack UI. Once all tasks pass, submit-implementation and invoke frontend-verify. If only source changes after an implementation/verification approval, use `refresh-evidence` instead of reopening design/tasks; the controller rejects source-only design/tasks reopen. If review fails, fix within scope and rerun affected checks and reviewer evidence. Governed risk also requires security-reviewer evidence before implementation approval.
