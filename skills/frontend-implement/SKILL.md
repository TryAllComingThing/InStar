---
name: frontend-implement
description: Implement authorized frontend tasks from reviewed specifications and design, with task-level verification. Use after planning, not for PRD or Spec authoring.
---

Read applicable `AGENTS.md` instructions from the project root through the target file's directory, plus any configured or discovered project architecture and design documents, relevant project `standards/` documents, and the selected change's current proposal, delta specs, `technical-design.md` and tasks. Inspect the existing package manifest, framework, components and build scripts before changing code. Preserve established architecture and naming; resolve a framework only when the project requires that decision. Implement approved loading, empty, error, responsive and accessibility states, keep business state and API boundaries explicit, and do not embed secrets or fabricate backend behavior. Context documents are optional: use the project's existing canonical locations or `.instar-quality.json` `context` paths; do not create duplicate copies to satisfy InStar. Confirm the user authorized implementation and that the planning artifacts are present. Do not infer permission from a task file alone. Project rules govern; plugin conventions fill gaps and never override them.

Use [InStar engineering references](../../standards/README.md) selectively. Identify the changed files' language and load only its guide from [language packs](../../standards/languages/README.md). For API work, consult [API design](../../standards/api/DESIGN.md) and [API security](../../standards/api/SECURITY.md); for persistence work, consult [database design](../../standards/database/DESIGN.md), [migrations](../../standards/database/MIGRATIONS.md), and the matching engine guide. For UI work, invoke [design-check](../design-check/SKILL.md) when a high-fidelity description or unresolved styling constraints need translation, then follow the target project's own design document, framework theme configuration, component library, token definitions, and existing UI patterns. Do not introduce frameworks, database abstractions, theme engines, token systems, or styling architectures unless the user or project requires them.

Work in dependency order. Before each task, inspect relevant existing components, tests, styles, and request/state boundaries. Follow the technical design's Architecture and File Change Plan against the current source tree. Prefer existing project patterns. For a new application, resolve its framework and setup in the first relevant task; this workspace does not choose one for you.

For observable behavior changes, add a focused failing test where the project supports a suitable test; then implement the behavior and run the test. Use browser/visual checks for UI outcomes that unit tests do not establish. Avoid tests that merely mirror implementation. If no suitable test framework or meaningful automated test exists (for example, a documentation-only or purely presentational change), state why and use proportionate alternative verification; do not add a test framework solely to satisfy TDD. Deliver each task's relevant tests and documentation with that task.

Route specialized work on demand: use [engineering-research](../engineering-research/SKILL.md) before adding a dependency, integrating an unfamiliar API, or writing a helper that may already exist; use [systematic-debugging](../systematic-debugging/SKILL.md) for unexplained failures or bugs. Use [context-optimizer](../context-optimizer/SKILL.md) only when project instructions are bloated, conflicting, stale, or causing repeated rediscovery. These skills supplement this implementation workflow; they do not replace its authorization, task evidence, TDD, or verification requirements.

Keep loading/error/empty states, accessible controls, keyboard behavior, and responsive layout aligned with the requirements. If implementation uncovers a requirement or design contradiction, report it and return to the affected planning stage; do not silently modify reviewed artifacts or fingerprint records.

Mark only completed canonical task checkboxes `[x]` after their acceptance evidence exists. Preserve task text and numbering; changing them invalidates the engine's fingerprint. Report completed work, actual verification and blockers. Use frontend-verify for final implementation checks. Do not promote or claim human acceptance on the user's behalf.

Read the [controller protocol](../requirements-workflow/references/controller.md). Require current implementation authorization before coding. Record each task via complete-task with actual evidence; do not check boxes directly. Use frontend-reviewer for read-only review when available. Once all tasks pass, submit-implementation and invoke frontend-verify. If review fails, fix within scope and rerun affected checks.
