# InStar v2.4 评审整改与发布建议

## 1. 文档目的

本文记录对 InStar v2.4 的多角色评审结论，回答三个问题：

1. 当前插件是否具备试点价值。
2. 在评审和发布前必须修改什么。
3. 哪些能力可以对外承诺，哪些能力不能夸大。

评审基于当前工作树截至 **2026-10-31** 的源码、Skill、控制器、Hook、测试和项目文档。本文是评审建议，不等同于产品验收或安全认证。

## 2. 评审结论

InStar 的核心方向成立：它是面向 AI 辅助研发的**软件交付控制层和证据编排层**，不是测试框架、安全扫描器、CI 引擎或企业身份审计平台。

当前版本适合在已有本地测试和构建工具的 Vue/TypeScript、Python 或 AI-first 团队中小范围试点；CI/GitHub 可作为远端增强，不是本地试点前置条件。不建议在当前工作树状态下直接进行全组织推广。

最有价值的能力是：

- PRD、Spec、技术设计、任务和人工审批的阶段控制。
- 审批哈希、上下文指纹和代码快照带来的证据新鲜度控制。
- 防止提交前后代码、Review、验证报告和 PR 的 SHA 不一致。
- 从存量代码生成带源码证据的当前状态 Spec。
- 对功能分支、默认分支、远端 base 和 CI 检查的保守约束。

最需要控制的风险是：

- Review 证据和审查者身份目前主要由调用方提供。
- 项目配置可以决定检查范围，插件不能证明配置覆盖了全部风险。
- 本地报告和 Skill trace 不是不可伪造的合规证据。
- 完整流程对低风险变更可能过重。
- 当前工作树删除了仍被引用的质量协议和发布文档。

## 3. 多角色讨论摘要

| 角色 | 共识 | 需要保留的限制 |
| --- | --- | --- |
| 产品负责人 | 能减少需求漂移、计划遗漏和交付证据缺失 | 小改动不应强制进入完整 PRD/Spec 流程 |
| 架构师 | 控制器、状态机、审批哈希和快照设计足以支撑试点 | 扩大范围前需要统一平台内核和适配器边界 |
| QA/安全负责人 | 能防止旧报告复用、工作树变化和错误分支发布 | 不能证明代码安全、Review 真实执行或测试覆盖充分 |
| 研发效能负责人 | 适合已有工具链的 AI 编程团队 | 首次接入、配置和失败诊断成本较高 |
| 交付经理 | 能形成从需求到 PR/CI 的复盘链路 | 必须定义审批角色、时限、豁免和责任边界 |
| 怀疑型评审 | 值得试点，但不能直接全面推广 | 需要用真实项目数据证明收益而非只统计流程活动 |

最终讨论共识是：**采用风险分级，L2/L3 变更重点使用 InStar，L0/L1 变更保持轻量路径。**

## 4. 评审前必须修改的事项

### P0：发布基线和文档一致性（已处理）

评审时发现以下文件被删除，但仍被 README、Skill、检查脚本或发布 Smoke Test 引用：

```text
docs/QUALITY.md
docs/EVALUATION.md
docs/PROVENANCE.md
docs/DEVELOPMENT-SKILLS.md
docs/REAL_MODEL_TESTING.md
THIRD-PARTY-NOTICES.md
```

本次 P0 修复已恢复这些发布契约文件，并保留原有引用路径：

- `node scripts/check.mjs` 已恢复通过。
- README、Skill、发布 Smoke Test 和文档链接继续使用稳定路径。
- 新增的插件评审和使用文档通过 README 入口访问，不替代质量协议和评估规范。

后续如果移动这些文件，必须同步更新所有引用、检查脚本和发布 Smoke Test；在变更完成前，不应发布不完整的文档包。

### P0：明确对外能力边界

README、Skill 和 PR 模板应统一使用以下表述：

- “验证通过”表示配置的检查命令成功，不表示代码没有缺陷。
- “AI Review 通过”表示辅助审查报告满足流程要求，不表示独立人工审查已经完成。
- “安全检查通过”只有在真实安全工具执行成功且对应 CI Check 受保护时才可使用。
- 本地 Hook 是辅助门禁，最终合并约束由 CI、分支保护和 CODEOWNERS 执行。
- `spec-discover` 描述代码现状，不等同于业务批准的目标需求。

### P1：增加变更风险分级（已处理；P0 加固完成）

已将变更路由定义为：

| 等级 | 变更范围 | 最低要求 |
| --- | --- | --- |
| L0 | 文案、注释、格式、非行为性文档 | 普通 PR 流程 |
| L1 | 局部 Bug、简单 UI、单模块重构 | 基本验证、Review、功能分支 |
| L2 | 跨模块、公开 API、权限、重要用户流程 | 轻量 PRD/Spec、技术设计、full verify、结构化 Review、人工审批；CI 可选 |
| L3 | 支付、认证、敏感数据、迁移、并发、基础设施 | 完整 PRD/Spec/任务、多角色审批、full verify、人工验收；CI 可选增强 |

质量控制器支持 `L0`–`L3` 的 `riskLevel`。除调用方声明外，控制器会根据内置敏感路径和 `riskPolicy.rules` 自动提升风险等级，禁止将已识别的高风险变更降级为 L1；L2/L3 自动要求 `full` profile。验证报告、Review 和统一质量报告都会记录风险等级，并阻断风险等级不一致的组合。

L3 还要求配置人工 Reviewer 角色和人工审批元数据；`requiredChecks` 及远端检查名称仅在项目接入 CI/GitHub 时配置。没有 CI 时，质量门禁仍校验本地 full verify、结构化 Review 和人工审批，并明确报告远端未接入。接入 CI 后，`ci publish/status` 才会校验 base 分支的 required status checks。身份真实性仍由外部身份系统、GitHub、CODEOWNERS 和分支保护提供，InStar 不伪造身份认证。

### P1：建立最小项目接入模板（已处理）

已新增可复制的 [`examples/quality/`](../examples/quality/) 示例，包括：

- `.instar-quality.json`。
- commit/full profile。
- 质量策略和 Q-01 至 Q-07 映射。
- 一个 TypeScript/Vue 或 npm 项目示例。
- 一个 Python 后端或跨栈项目示例。
- 可选的 CI required checks、`baseRef` 和 `secretCheck` 示例。

模板同时说明 L0–L3 路由、L2/L3 Review 命令、Q-01 至 Q-07 映射、本地优先流程和可选 CI required checks 的接入边界；项目仍需按实际工具和风险修改配置。

### P1：加强证据真实性（第一阶段已处理；L3 外部门禁已加固）

第一阶段已完成：

1. L2/L3 Review evidence 使用结构化对象，包含 `type`、`note`、`snapshotFingerprint`、相对文件路径、行号和当前源码摘录。
2. 运行时校验证据路径安全、行号范围、摘录与当前工作区文件内容一致，并要求 fingerprint 与 Review 一致。
3. 验证报告和 Review 的风险等级必须一致，避免用低风险报告覆盖高风险变更。

仍待后续阶段处理的事项：

1. 区分作者、AI Reviewer、人工 Reviewer 和 CI 机器人身份，并引入不可抵赖的身份证明。
2. 对安全、数据迁移、权限和发布相关变更要求独立人工审查。
3. 将 HMAC 密钥从项目检查命令环境中隔离，优先由受保护 CI 生成签名。

## 5. 可以推迟的事项

以下事项对组织化推广重要，但不应阻塞第一轮试点：

- GitHub 以外的 CI/代码托管适配器。
- Rust、Kotlin、Ruby、C# 等语言专项 Review。
- 完全配置化的工作流状态机。
- 集中式组织策略和多仓库配置服务。
- 不可变远端审计存储。
- Skill trace 的完整哈希链。
- 所有 Review 结论的自动语义验证。

## 6. 试点验收条件

试点前提：

- 目标仓库已有可运行的 lint、类型检查、测试和构建；安全检查按项目实际能力配置。
- 目标仓库不使用真实生产凭据或强监管数据。
- 项目负责人确认 `.instar-quality.json` 的检查范围。
- 人工 Reviewer 明确知道 AI Review 只是辅助信号。

CI/GitHub 是可选的试点增强条件。若已接入，才额外要求功能分支、远端 required checks、分支保护和允许的认证环境；未接入时，试点范围必须明确为本地验证和人工审批。

试点成功应同时满足：

- L2/L3 变更的验证和 Review 证据与最终 PR HEAD 一致。
- 过期报告和提交后代码变化能够被阻断。
- 小改动的交付周期没有明显恶化。
- 需求遗漏、接口遗漏或验证遗漏造成的返工趋势下降。
- 团队能区分 `FAIL`、`BLOCK`、`WARN`、`NA` 和“未配置”。
- 没有出现为追求 PASS 而弱化检查配置的行为。

建议先建立四周基线，再进行四到八周试点。没有基线数据，不应把“报告数量增加”或“Review 通过率上升”当作成功。

## 7. 建议跟踪的指标

### 交付效率

- 首次项目接入时间。
- 首次成功 PR 的周期。
- PR Review 往返次数。
- 本地验证耗时 P50/P95。
- CI 失败定位时间（仅对已接入 CI 的项目统计）。

### 质量结果

- 需求遗漏导致的返工次数。
- 合并后缺陷和回滚数量。
- 权限、API、迁移和测试问题在合并前发现的比例。
- 代码验证后再次修改的次数。

### 流程健康度

- 过期证据阻断次数。
- 配置错误导致的阻断次数。
- 豁免率和豁免后补救完成率。
- 有效 Hook 阻断率。
- 开发者绕过流程的比例。

## 8. 发布决策

在以下条件全部满足前，建议保持“受控试点”状态；本轮已完成技术验证与发布链加固，但真实项目试点和 ROI 仍待完成：

1. 当前文档删除与引用关系已处理。✅
2. `node scripts/check.mjs`、构建、发布 Smoke Test 和 `npm run release` 通过；发布包已生成 `RELEASE-PROVENANCE.json`。✅
3. 至少一个真实项目完成端到端试点。
4. 证据边界和不能夸大的声明已写入用户文档。
5. 试点数据证明质量收益高于流程成本。

届时可以从“试点版”升级为“团队级交付控制层”；在此之前，不应宣传为企业级质量、合规或安全平台。
